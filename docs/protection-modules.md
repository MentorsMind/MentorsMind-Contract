# Protection module → contract mapping

`contracts/shared/src/lib.rs` declares 35 `pub mod` protection/utility
modules. This document maps each one to the contracts that actually import
symbols from it, so a reviewer can answer "what protects this contract?"
and "does anything still use this module?" without grepping the whole
workspace by hand (#987).

## Methodology

Generated by matching each contract's `use shared::{...}` (and
`use shared::<module>::{...}`) import list against the symbol lists
`contracts/shared/src/lib.rs` re-exports for each module (its
`pub use <module>::{...}` block), then verified against the actual file
contents. Two caveats that matter if you extend this table:

1. **`events` is never flat re-exported** — every contract that uses it
   imports via the qualified path `shared::events::{...}` instead of a bare
   `shared::{...}` name. It's listed separately below since the automated
   module→symbol match can't see it.
2. **Trait imports can look unused and not be.** A trait like `StateMachine`
   or `SafeMath` is only ever referenced by name at the `use` line — calling
   its methods (`EscrowStatus::transition(...)`, `x.safe_mul(...)`) never
   repeats the trait's name in the source. A naive "does this identifier
   appear more than once" check flags these as dead imports; they are not.
   Any removal must be verified by checking whether the module defines a
   `pub trait` before trusting an occurrence count of 1.

## Genuinely unused modules

Three modules are declared and re-exported but not imported — by symbol
name *or* qualified path — anywhere in the workspace:

- **`governance_voting`** — commit-reveal voting primitives
  (`VoteCommitment`, `calculate_voting_weight`, ...). `contracts/governance`
  implements its own voting logic inline rather than using this module.
- **`interface_id`** — canonical interface-ID constants
  (`ESCROW_INTERFACE_ID`, etc.) intended to pair with `interface_registry`.
  `contracts/interface_registry` does not currently import them.
- **`ttl_utils`** — TTL/storage-lifetime management helpers
  (`TTLManager`, `next_bump_interval`, ...). Every contract manages its own
  `extend_ttl` calls directly instead.

These are left in place rather than deleted: each looks like it was built
ahead of an integration that didn't happen yet (or happened via a
different, ad hoc mechanism), not dead code from a removed feature.
Deleting them would be a larger, separate decision than this pass covers.
If a future contract genuinely needs interface-ID constants or TTL
bookkeeping, wiring these modules in is preferable to reinventing them.
